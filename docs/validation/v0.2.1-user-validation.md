# v0.2.1 真实用户验证 Sprint

- 版本：`v0.2.1`（tag 不得移动、删除或重建）
- 状态：**模板已就绪，等待真实测试数据**
- 前置验收：[v0.2 十家公司技术验收](v0.2-real-company-evaluation.md)

> 上一轮验收由工程师选公司、工程师判断质量，验证的是**系统是否诚实**。
> 这一轮由真实货代销售选公司、销售判断质量，验证的是**产品是否有用**。
> 两者结论不能互相替代。

## 1. 测试目标

**要回答的唯一问题：一个真实的货代销售，愿不愿意在下周继续用它？**

拆成三个可测量的子问题：

| # | 问题 | 主指标 |
|---|---|---|
| 1 | 它是否真的省时间？ | 单家总耗时 vs 该测试者自己的手工基线 |
| 2 | 产出是否可直接用于销售？ | 可用邮件率、直接接受率 |
| 3 | 审核负担是否可接受？ | 人工审核时长、手工补充字段数 |

**明确不在本轮验证范围**：抽取器的召回上限、评分阈值是否最优、多数据源覆盖。
这些需要先有真实使用数据才能校准，本轮只负责产生那批数据。

## 3. 测试执行清单

每家公司完整走一遍，中途不跳步。

### 3.0 环境准备（操作者执行一次）

- [ ] 根目录 `.env` 设置 `NEXT_PUBLIC_ENABLE_RESEARCH=true`
- [ ] **重建前端**：`docker compose build --no-cache frontend && docker compose up -d frontend`
      （`NEXT_PUBLIC_*` 是构建期内联，只重启容器不生效——v0.2.1 修的就是这个）
- [ ] 如需真实抽取：`RESEARCH_EXTRACTOR_PROVIDER=openai`；否则默认 Fake
- [ ] 确认 Research API **未**暴露到公网（ADR-0026）

### 3.1 完整用户路径

| 步骤 | 动作 | 记录 |
|---|---|---|
| 1 | 输入公司名 + 官网，点击「开始自动研究」 | 开始时刻 |
| 2 | 等待研究结束 | **system latency** |
| 3 | 查看抓取到的页面与来源 | 来源是否可信 |
| 4 | 逐条审核 Claim：接受 / 修改 / 拒绝 | 各类计数 |
| 5 | 点击「确认并填入下方表单」 | **human review time** 到此为止 |
| 6 | 补充联系人与发件人信息 | **手工补充字段数** |
| 7 | 点击「分析潜在客户」 | |
| 8 | 查看资格评估结果 | **qualification result** |
| 9 | 查看邮件草稿 | **email usability** |
| 10 | 批准草稿 | |
| 11 | 刷新页面确认状态恢复 | 是否丢数据 |
| — | 全流程结束 | **total workflow time** |

### 3.2 选样规则

- **必须是测试者自己真实想开发的公司**，不得使用合成公司或本仓库已验收过的十家。
- 目标 **20–30 家**，类别分布由测试者按自己的实际业务决定，不预设配额。
- 允许包含"预期不好做"的公司（JS 重站、信息稀少的小公司）——真实分布比漂亮数据重要。
- 逐家串行，不并发。

### 3.3 测试者需提前知悉的已知限制

告知这些不是为了降低期待，而是为了让反馈落在**可改进的地方**：

- 官网无法证明进口记录、货量、供应商——这类信息本轮拿不到。
- `china_dependency` 多数会是 Unknown（技术验收中十家里九家如此），需要海关数据源。
- JS 重度站点会返回 `needs_browser`，不是失败而是如实报告。
- 每条 Claim 都必须人工审核，系统不会自动采纳。
- 系统永不发送邮件。

## 5. 指标定义

定义先于数据。以下口径在收集数据前固定，收集后不得为了让数字好看而修改。

| 指标 | 定义 | 口径说明 |
|---|---|---|
| **research success rate** | (completed + 有用 partial) / 总运行数 | "有用 partial" = 状态 partial 且至少产出 1 条通过校验的 Claim |
| **average system latency** | 步骤 1→2 耗时均值 | 纯机器时间，不含人看结果的时间 |
| **average human review time** | 步骤 3→5 耗时均值 | 从结果出现到点击「确认并填入表单」，不含 system latency |
| **accepted rate** | accepted / 通过校验的 Claim 总数 | **直接**接受，不含 edited |
| **accepted + edited retention** | (accepted + edited) / 通过校验的 Claim 总数 | 衡量"提案是否值得留下" |
| **average manual fields added** | 应用 Claim 后仍需人工填写/修正的字段数均值 | 含联系人、发件人、缺失来源、需改写的 signal |
| **qualified rate** | QUALIFIED 家数 / 完成分析家数 | |
| **usable email rate** | (`send-as-is` + `light-edit`) / 生成草稿总数 | 只有这两档算"可用" |
| **estimated time saved** | 该测试者手工基线 − total workflow time | **必须用该测试者自己的实测基线**，不得跨测试者混用 |
| **repeat-use willingness** | 愿意下周继续使用的测试者数 / 测试者总数 | 见 §6 问题 1 |

## 6. 用户反馈表

每位测试者在完成全部公司后填写一次。**记录原话，不要替测试者润色。**

1. **下周你还会用它吗？为什么？**（这一题的答案比其他所有指标加起来更重要）
2. 最省时间的是哪一步？
3. 最浪费时间的是哪一步？
4. 有没有哪一次你**不相信**系统给的结论？当时发生了什么？
5. 邮件草稿最常需要改什么？
6. 审核 Claim 时，信息够不够你做判断？缺什么？
7. 如果只能修一个问题，你要修哪个？
8. 你会把它推荐给同事吗？会怎么描述它？

## 7. 问题分级规则

**只根据真实测试中实际发生的现象立项，不得基于推测或"将来可能"立项。**
每条问题必须能指向具体的公司编号与复现步骤。

### P0 — 发布阻断

- 阻断完整流程：任一步骤无法完成，且无绕过方式
- 安全泄露：凭据、系统提示词、内部端点、他人数据出现在页面或响应中
- 数据丢失：已批准的草稿、已确认的 Claim 或分析结果在刷新后消失或被覆盖

### P1 — 影响可用性

- 明显增加销售工作量（例如手工补充字段数高于自己写还多）
- 结果难以理解（销售看不懂为什么是这个结论）
- 审核效率低（逐条审核耗时超过自己直接判断的时间）

### P2 — 体验问题

- 视觉、文案、排版
- 非关键路径的交互不顺手

## 8. v0.2.2 发布决策标准

**先定标准，再看数据。** 以下阈值在收集数据前确定。

### 必要条件（全部满足才考虑发布 v0.2.2）

| # | 条件 | 阈值 |
|---|---|---|
| 1 | P0 问题 | **0 个未解决** |
| 2 | research success rate | ≥ 80% |
| 3 | usable email rate | ≥ 50% |
| 4 | accepted + edited retention | ≥ 70% |
| 5 | estimated time saved（中位数） | **> 0 且 ≥ 手工基线的 30%** |
| 6 | repeat-use willingness | **≥ 2/3 测试者回答"会"** |
| 7 | 全部自动化门禁 | 全绿 |

第 5、6 条是产品性判断，不能用工程指标替代：**如果销售不省时间、下周不想再用，
其余数字再漂亮也不构成发布理由。**

### 决策矩阵

| 情况 | 结论 |
|---|---|
| 全部必要条件满足 | 修完 P1 后发布 v0.2.2 |
| 仅 P1 未达标，P0=0 且第 5、6 条满足 | 按 P1 排序修复，再复测该项后发布 |
| 第 5 或第 6 条不满足 | **不发布**。回到问题定义：省时间的假设本身需要重新验证 |
| 存在未解决 P0 | **不发布**，无例外 |

### 样本量说明

20–30 家、2–3 位测试者是**方向性验证**，不是统计显著性验证。任何比率指标都应
连同分母一起报告（例如"可用邮件率 60%（12/20）"），不得只写百分比。

## 9. 数据与隐私约束

- 不记录测试者姓名、公司、邮箱、电话或任何可识别个人的信息，只记录角色编号。
- 被研究公司的**公开官网信息**可以记录；**不得**记录通过其他渠道获得的私人联系方式。
- 不保存网页正文，只保留证据片段（沿用技术验收的做法）。
- 邮件草稿正文不完整抄录进本文档，只记录可用性档位与需要修改的类型。
